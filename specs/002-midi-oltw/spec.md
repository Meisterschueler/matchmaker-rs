# Feature Specification: MIDI Online Time Warping (arzt, dixon)

**Feature Branch**: `002-midi-oltw`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "Port the MIDI score followers `arzt` (OnlineTimeWarpingArztEvent) and
`dixon` (OnlineTimeWarpingDixonEvent) of pymatchmaker v0.4.0 to Rust, on top of the existing
MIDI pipeline (processor `chord_onset`, MusicXML and MIDI scores). Same quality gates as
feature 001: golden parity, visible performance, debuggability, library/CLI/Python interfaces."

Builds on [001-midi-score-following](../001-midi-score-following/spec.md); terms and quality gates
defined there are not repeated.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Follow a MIDI performance with `arzt` (Priority: P1)

A developer has a score (MusicXML or MIDI) and a recorded MIDI performance. They select the
`arzt` method and receive, per consumed observation, the current score position in beats, and at
the end the alignment path. The follower aligns chords of the performance (merged by
`chord_onset`) against one binary pitch vector per unique score onset.

**Why this priority**: First of the two missing MIDI methods and the one that also underlies the
later audio OLTW family.

**Independent Test**: Run `arzt` on the bundled `simple_mozart_k265_var1` and compare positions
and alignment path with the reference output.

**Acceptance Scenarios**:

1. **Given** the bundled score and performance, **When** `arzt` runs in simulation mode,
   **Then** positions and alignment path equal the reference.
2. **Given** a MIDI score instead of MusicXML, **When** `arzt` runs, **Then** positions lie on
   the same onset grid as the reference.
3. **Given** the CLI, **When** the developer passes `--method arzt`, **Then** the processor
   defaults to `chord_onset` and positions are printed as for the other methods.

---

### User Story 2 - Follow a MIDI performance with `dixon` (Priority: P1)

Same workflow as User Story 1 with the `dixon` method (sparse cost matrix, path-length
normalisation, run-count limits).

**Why this priority**: Second missing MIDI OLTW method; shares the score features and stream
wiring of User Story 1.

**Independent Test**: Run `dixon` on the bundled example and compare with the reference output.

**Acceptance Scenarios**:

1. **Given** the bundled score and performance, **When** `dixon` runs, **Then** positions and
   alignment path equal the reference.
2. **Given** a score with fewer onsets than the search window, **When** `dixon` runs, **Then**
   it behaves as the reference does and does not crash.

---

### User Story 3 - Prove parity and compare performance (Priority: P1)

A maintainer wants the same evidence for `arzt` and `dixon` as for the 001 methods: golden
parity and side-by-side latency against the Python reference.

**Why this priority**: Reference parity and visible performance are non-negotiable
(constitution I, III).

**Independent Test**: `cargo test --workspace --exclude matchmaker-py` runs golden tests for both
methods; the benchmark report lists them next to `pthmm`, `hmm`, `outerhmm`.

**Acceptance Scenarios**:

1. **Given** reference outputs generated by the pinned release, **When** the Rust tests run,
   **Then** score features, observations, positions and alignment paths match within documented
   tolerances and a mismatch names the first differing observation.
2. **Given** the benchmark datasets, **When** the benchmark runs, **Then** the report contains
   latency, real-time factor, accuracy and alignment parity for `arzt` and `dixon`.

---

### User Story 4 - Use them from CLI, Python and the debug export (Priority: P2)

A user selects `arzt` or `dixon` in the CLI and the Python package, overrides their parameters,
and exports intermediate data.

**Why this priority**: Constitution: delivered methods must be drop-in in the bindings and
debuggable; it needs the library part first.

**Independent Test**: The README quickstart with `method="arzt"` / `"dixon"` and
`input_type="midi"` returns the same positions as the library.

**Acceptance Scenarios**:

1. **Given** the Python package, **When** `Matchmaker(..., input_type="midi", method="arzt")`
   runs, **Then** it yields positions and the alignment path in the reference's shapes.
2. **Given** `--set window_size=…` (or `kwargs`), **When** a run starts, **Then** the parameter
   reaches the follower exactly as in the reference; unknown parameters are rejected with the
   list of valid ones.
3. **Given** export enabled, **When** a run finishes, **Then** the score onset features,
   observations, per-step position and alignment path are written in a Python-readable format.
4. **Given** `input_type="audio"`, **When** requested, **Then** the existing error lists the
   supported options (audio stays unsupported).

### Edge Cases

- Performance contains notes not in the score: no insertion states exist in OLTW; behaviour
  matches the reference.
- Empty performance or without note-ons: empty alignment path, no error.
- Performance ends before or continues after the end of the score: positions stay within the
  score; stop rule per reference run loop.
- Score with a single onset: it is already at its last state, so the run loop never calls the
  follower and the path stays empty, as in the reference. Window larger than the number of
  onsets: no error, positions stay within the score.
- Observation with no active pitch (distance undefined, e.g. cosine of a zero vector): same
  result as the reference.
- Unreadable or corrupt files: typed error as in 001.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide the methods `arzt` and `dixon` for MIDI input, selectable by
  these names, with the reference defaults for MIDI (processor `chord_onset`, 1 ms polling,
  `piano_range` on) and with the reference's rules for which parameters reach the follower.
- **FR-002**: System MUST build the score reference as the reference does: one binary pitch
  vector per unique score onset (88 keys, or 128 without `piano_range`) plus the onset beat of
  each row.
- **FR-003**: `arzt` MUST follow `OnlineTimeWarpingArztEvent`: windowed rolling-column DP over
  onsets with cosine distance by default, window size, start window size and step size as
  parameters.
- **FR-004**: `dixon` MUST follow `OnlineTimeWarpingDixonEvent`: sparse cost matrix,
  path-length-normalised catch-up, `window_size`, `max_run_count` and `distance_func` as
  parameters.
- **FR-005**: For every consumed observation the follower MUST report the score position in
  beats; at the end it MUST return the alignment path. Stop rules and which observations add a
  path entry follow the reference run loop of each method.
- **FR-006**: Method parameters MUST be overridable via library, CLI (`--set`) and Python
  (`kwargs`); invalid names or values MUST give a typed error.
- **FR-007**: System MUST include golden tests for both methods and for the onset features,
  generated by the checked-in script from the pinned reference release (constitution I).
- **FR-008**: The benchmark MUST cover both methods with the same metrics as the other methods.
- **FR-009**: The CLI and the Python `Matchmaker` MUST support both methods for MIDI input; the
  001 tests that expect `method="arzt"` to fail MUST be updated.
- **FR-010**: System MUST export score onset features, per-step positions and the alignment
  path for both methods (constitution IV) and instrument the steps with `tracing` (III).
- **FR-011**: README (methods table, roadmap) and `UPSTREAM.md` (module map, "Not ported") MUST
  be updated.

### Key Entities

- **Onset pianoroll**: matrix with one binary pitch vector per unique score onset and the vector
  of their onset beats.
- **Cost state**: per method, the accumulated alignment cost over (score onset, performance
  event) cells, kept only as far as the reference keeps it.
- **Alignment path**: as in 001.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On all bundled examples and all benchmark dataset pieces, 100% of positions of
  `arzt` and `dixon` equal the reference positions (difference < 1e-6 beats), or every
  deviation is explained and the evaluation metrics differ by at most 0.01.
- **SC-002**: Onset features equal the reference for 100% of rows of the bundled examples.
- **SC-003**: Mean inference latency per observation in Rust is at least 5× lower than the
  reference on the same machine, as shown in the benchmark report.
- **SC-004**: For any parity failure the test output names the method, the input and the index
  of the first differing observation.
- **SC-005**: The 001 test suite and golden data stay green except for the tests that asserted
  `arzt` as unsupported.

## Assumptions

- Reference: pymatchmaker `v0.4.0`, same lock file as 001; both methods are deterministic.
- Event-level `arzt` and `dixon` only; frame-level (audio) variants, tempo models for OLTW,
  `arzt_multi_fold`, `pfkorz` and the parangonar methods are out of scope.
- The processor `chord_onset` and the stream modes of 001 are reused unchanged; no new MIDI
  processor is needed (the onset pianoroll is score-side).
- Defaults are those the reference actually passes (`methods.yaml` after its pass-through
  exclusions), not those printed in the YAML comments; any discrepancy is documented in the plan.
- The Python reference computes distances with SciPy in `float32`/`float64` mixes; the plan
  decides how far bit-level parity goes, following the approach of 001 (R4).
